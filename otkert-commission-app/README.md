# ÖTKERT Commission Tracker

A commission tracking web app that replaces the `otkert jutalek nyilvantartas.xlsx`
spreadsheet as the day-to-day interface, while keeping Google Sheets as the
permanent database.

```
Mobile / Desktop Browser
      │
      ▼
HTML Web App (frontend/)  — vanilla HTML/CSS/JS, no framework
      │  fetch() calls
      ▼
Google Apps Script API (backend/Code.gs)  — JSON API, deployed as a Web App
      │  SpreadsheetApp
      ▼
Google Sheets  — the single source of truth
```

Nothing important is stored in the browser. Every screen re-reads from
Google Sheets on load and after every save, edit, delete, or settings
change, so the same data shows up whether you open the app on an iPhone or
a desktop.

---

## A. Google Sheets structure

Create **one** Google Sheet (any name, e.g. "ÖTKERT Jutalék Nyilvántartás").
The setup script (`backend/Code.gs → setupSheets()`) creates and formats
these three tabs for you — you don't need to build them by hand:

### `Daily_Data` (the actual records)

| ID | Date | Used Codes | Commission Rate | Commission | Created At | Updated At |
|----|------|-----------|------------------|-------------|------------|------------|
| 1  | 2026-08-01 | 12 | 500 | 6000 | 2026-08-01 09:14 | 2026-08-01 09:14 |

- **ID, Commission Rate, Commission, Created At, Updated At** are all
  generated by the backend — the app never asks you to type them, and you
  shouldn't hand-edit them in the Sheet either (those columns carry a
  "warning" protection so editing them prompts a confirmation).
- Only real rows exist. No blank rows are pre-created — if you have 12
  records, the sheet has 12 data rows.
- `Commission Rate` is stored **per record**, frozen at the rate active on
  the day it was saved. This is what makes a future rate change (500 → 600)
  apply only to new records without silently rewriting old totals.

### `Settings`

| Setting | Value |
|---|---|
| Commission per Code | 500 |

The app reads this value for every calculation — it is never hardcoded in
the JavaScript or Apps Script.

### `Monthly_Summary`

| Month | Used Codes | Commission |
|---|---|---|
| August 2026 | 85 | 42500 |

Regenerated automatically after every add/edit/delete, purely so the raw
Sheet itself stays readable if you ever open it directly. The app's
dashboard does **not** depend on this tab — it computes the same numbers
live from `Daily_Data` on every load, so it's always accurate even if this
tab were cleared.

## B. Backend (Google Apps Script)

All backend code lives in `backend/`:

- `Code.gs` — the full API: reading, adding, editing, deleting records;
  reading/updating settings; computing dashboard + monthly summaries;
  server-side validation; sheet setup/formatting.
- `appsscript.json` — the project manifest (timezone, web app access).

## C–E. Frontend (HTML / CSS / JS)

All frontend code lives in `frontend/`:

- `index.html` — page structure and all four views (Dashboard, Add Record,
  History, Settings).
- `style.css` — mobile-first responsive styling (see the breakpoints at the
  bottom of the file: base/mobile, `768px`, `1024px`).
- `app.js` — all frontend logic: API calls, rendering, validation, edit/
  delete flows, loading states, toasts.
- `config.js` — the **one file you edit** to point the app at your
  deployed Apps Script Web App URL.

## F. Setup instructions

### 1. Create the Google Sheet

1. Go to [sheets.google.com](https://sheets.google.com) → **Blank
   spreadsheet**.
2. Rename it, e.g. "ÖTKERT Jutalék Nyilvántartás".
3. Leave it otherwise empty — the setup script builds the tabs for you.

### 2. Open Google Apps Script

1. In the Sheet, go to **Extensions → Apps Script**. This opens a script
   project already bound to your spreadsheet.
2. Delete the placeholder `Code.gs` content (the default `myFunction()`
   stub).

### 3. Paste the backend code

1. Copy the full contents of `backend/Code.gs` from this repo and paste it
   into the `Code.gs` file in the Apps Script editor.
2. In the Apps Script editor, click the **⚙ Project Settings** gear on the
   left, and if you'd like the manifest to match exactly, you can also open
   `appsscript.json` (enable "Show appsscript.json manifest file" under
   Project Settings) and paste in `backend/appsscript.json`. This step is
   optional — the deployment dialog in step 5 sets the same access options.

### 4. Run the one-time setup

1. In the function dropdown at the top of the editor, select
   **setupSheets**.
2. Click **Run** (▶). The first run will prompt for authorization:
   - Click **Review permissions** → choose your Google account → **Advanced**
     → **Go to (project name) (unsafe)** → **Allow**. This warning is
     normal for scripts you write yourself; it's your own script accessing
     your own Sheet.
3. Switch back to the Google Sheet tab — you should now see three tabs:
   `Daily_Data`, `Settings`, `Monthly_Summary`, each with a frozen, bold
   header row and a default commission rate of `500` in `Settings`.

### 5. Deploy the Apps Script as a Web App

1. Back in the Apps Script editor, click **Deploy → New deployment**.
2. Click the gear icon next to "Select type" and choose **Web app**.
3. Fill in:
   - **Description**: e.g. "ÖTKERT Commission API v1"
   - **Execute as**: **Me** (your account) — so the script can write to
     the Sheet regardless of who opens the web app.
   - **Who has access**: **Anyone** — this does *not* expose your Sheet
     publicly; it only allows the app's `fetch()` calls to reach this
     specific API endpoint. There's no built-in listing/browsing of your
     Sheet data outside the functions defined in `Code.gs`.
4. Click **Deploy**, authorize again if prompted, then copy the **Web app
   URL** shown (it looks like
   `https://script.google.com/macros/s/AKfycbxxxxxxxxxxxxxxxxxxxx/exec`).

   > If your organization requires Google account sign-in for internal
   > tools, choose **Anyone within [your organization]** instead — the app
   > will then require the user to be signed into a Google account in your
   > org before it can call the API.

### 6. Put the Web App URL into the frontend

1. Open `frontend/config.js`.
2. Replace the placeholder with your URL:
   ```js
   var CONFIG = {
     API_URL: 'https://script.google.com/macros/s/AKfycbxxxxxxxxxxxxxxxxxxxx/exec'
   };
   ```
3. Save the file.

### 7. Host the frontend

The frontend is three static files (`index.html`, `style.css`, `app.js`,
`config.js`) — any static hosting works:

- **GitHub Pages** (recommended, free): push this `frontend/` folder to a
  repo, enable Pages on it, and open the resulting URL on any device.
- **Google Drive / any static host**: also fine, as long as it's served
  over `http(s)://`, not opened as a local `file://` path (some browsers
  block `fetch()` from `file://` pages).

### 8. Test the connection

1. Open the hosted `index.html` URL.
2. The Dashboard should load with all KPIs at `0 HUF` / `0` (since there's
   no data yet) instead of showing the "not connected" banner.
3. If you see **"The app is not connected yet"**, double check
   `config.js` was saved with the real URL (not the placeholder) and that
   you re-deployed/re-hosted after editing it.
4. If you see **"Something went wrong. Please try again."**, open the
   Apps Script editor → **Executions** (left sidebar) to see the actual
   server-side error and stack trace.

### 9. Verify records are written to Google Sheets

1. In the app, go to **Add Record**, enter today's date and a code count
   (e.g. `12`), confirm the commission preview shows `6,000 HUF`, and tap
   **Save Record**.
2. Switch to the **History** tab in the app — the record should appear
   immediately.
3. Open the Google Sheet directly and check the `Daily_Data` tab — the same
   row should be there, with `ID`, `Commission Rate`, `Commission`,
   `Created At`, and `Updated At` all filled in automatically.
4. Open the app from a second device (or a different browser) — the same
   record should be visible there too, confirming Sheets (not local
   storage) is the source of truth.

### 10. Updating the app later

- **Backend changes**: edit `Code.gs` in the Apps Script editor, then
  **Deploy → Manage deployments → (pencil icon) → New version → Deploy**.
  Editing the script without creating a new version does *not* update the
  live `/exec` URL.
- **Frontend changes**: edit the files in `frontend/` and re-upload/re-push
  to wherever you're hosting them (e.g. `git push` for GitHub Pages).
- **Commission rate changes**: no code change needed — use the app's
  **Settings** tab.

## Migrating your existing spreadsheet data

Since no historical data file was available when this app was built, no
records were pre-loaded — `Daily_Data` starts empty and grows from what you
enter. To bring in your existing history from `otkert jutalek
nyilvantartas.xlsx`:

- **Small number of records**: just re-enter them one by one via **Add
  Record** in the app — each save is validated and calculated
  automatically.
- **Larger history**: open the `Daily_Data` tab in the Google Sheet
  directly and paste your old (Date, Used Codes) pairs into columns B and
  C for as many rows as you have real data, **starting at row 2**. Then,
  for just those pasted rows, fill in column A (ID) with unique increasing
  numbers, column D (Commission Rate) with the rate that was active on that
  date, column E (Commission) with `Used Codes × Commission Rate`, and
  columns F/G (Created At / Updated At) with the original date. Reload the
  app afterward — it will pick up the pasted rows exactly like ones added
  through the UI. Do not leave any blank rows between or above your data.

## Design notes

- **Rate changes don't rewrite history**: each record keeps the commission
  rate that was in effect when it was saved, so changing the rate in
  Settings only affects records you add afterward.
- **No client-side data cache**: `app.js` never writes records to
  `localStorage`; every view reflects the latest `fetch()` from Apps
  Script.
- **Server-side validation**: `Code.gs` re-validates date and used-codes on
  every add/update, independent of the frontend's own validation — a
  malformed request can't corrupt the Sheet.
- **Mobile-first**: the CSS starts from a single-column, touch-friendly
  layout (44px+ tap targets, 16px inputs to avoid iOS zoom-on-focus, bottom
  tab bar) and widens into a desktop table/nav layout at `768px` and
  `1024px`.
